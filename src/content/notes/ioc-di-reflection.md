## 1. IoC — 제어권은 누가 갖는가

IoC(Inversion of Control)는 "객체를 누가 만들고, 의존 관계를 누가 결정하는가"에 대한 답이 뒤집힌 것을 말한다.

```java
// IoC 없음 — 객체가 자기 의존성을 직접 만듦
class OrderService {
    private RealPaymentClient paymentClient = new RealPaymentClient("https://real-payment-api.com");
}
```

```java
// IoC 적용 — 의존성을 밖에서 받기만 함
class OrderService {
    private final PaymentClient paymentClient;
    OrderService(PaymentClient paymentClient) { this.paymentClient = paymentClient; }
}
```

전자는 `OrderService`가 "무엇을 쓸지"와 "어떻게 만들지"를 둘 다 스스로 결정한다. 후자는 "무엇을 쓸지(타입)"만 선언하고, "어떻게 만들지"는 외부(스프링 컨테이너)에게 넘긴다. 이 생성/조립의 제어권이 객체 자신에서 외부로 넘어간 것이 IoC다.

IoC는 사실 의존성 주입보다 더 큰 개념이다. 원래는 "누가 프로그램의 흐름을 제어하는가"에 대한 일반적인 개념으로, 프레임워크가 내 코드를 호출하는 방식(할리우드 원칙: "먼저 연락하지 마세요, 저희가 연락드릴게요") 자체를 가리켰다. 2004년 Martin Fowler가 이 개념 중 "의존성 생성에 대한 제어권 역전"만 따로 떼어 **DI(Dependency Injection)**라는 이름을 붙여 구분했다.

## 2. 직접 생성이 만드는 진짜 문제

`OrderService`가 `RealPaymentClient`를 직접 `new`하면:

- **교체 불가능**: 테스트에서 가짜(mock)로 바꾸려 해도 `OrderService`를 만드는 순간 실제 결제 API 클라이언트가 함께 만들어진다. 테스트를 돌릴 때마다 진짜 외부 API로 요청이 나갈 수 있다.
- **강한 결합**: `OrderService`가 `RealPaymentClient`의 생성자 파라미터(URL 등)까지 알아야 한다.
- **재사용 불가**: 같은 인스턴스를 다른 곳과 공유하고 싶어도 각자 `new`하면 매번 별개 객체가 된다.

이 문제를 피하려고 "테스트용 클래스"를 따로 만들면 어떻게 될까 — 상속으로 생성 로직을 오버라이드하거나, 클래스 내부에 `isTestMode()` 같은 분기를 심는 수밖에 없다. 둘 다 결국 "생성을 밖으로 빼는" DI를 어설프게 재발명하는 것이거나, 테스트 코드가 운영 코드를 오염시키는 안티패턴이다.

이건 SOLID의 **DIP(의존 역전 원칙)** 위반의 증상이다: "상위 모듈은 하위 모듈의 구체 구현이 아니라 추상화에 의존해야 한다." `OrderService`(상위, 비즈니스 로직)가 `RealPaymentClient`(하위, 구체 구현)를 직접 알아버리는 순간 이 원칙이 깨진다.

IoC/DI가 DIP를 해결하려고 발명된 것은 아니다. 순서는 반대에 가깝다 — IoC/DI(제어권을 밖으로 넘기는 기법)를 적용하면, 결과적으로 DIP(구체 구현에 의존하지 않는다는 설계 원칙)도 자연스럽게 만족된다.

## 3. DI — 주입 방식 세 가지와 권장 이유

- 생성자 주입 (권장)
- 필드 주입 (비권장)
- 세터 주입 (선택적 의존성일 때만)

생성자 주입을 권장하는 이유를 실무 임팩트 순으로 정리하면:

1. **스프링 없이 순수 자바로 테스트 가능** — `new OrderService(mockPaymentClient)`로 컨테이너 없이 빠른 단위 테스트 작성 가능. 매일 체감되는 생산성 차이.
2. **순환 참조를 시작 시점에 즉시 에러로 발견** — A가 B를, B가 A를 필요로 하면 스프링이 앱을 아예 못 띄우고 `BeanCurrentlyInCreationException`을 던진다. 필드 주입은 이걸 "일단 빈 객체 둘 다 만들고 나중에 채워넣기"로 우회해버려서, 순환 의존이라는 설계 결함이 앱이 정상 기동한 채로 숨겨진다.
3. **`final` 선언 가능** — 컴파일러가 "이 필드는 생성자에서 딱 한 번만 대입 가능"을 강제한다. `final` 없이는 클래스 내부 어떤 메서드에서든 재대입이 컴파일 에러 없이 가능해서, "이 의존성이 런타임 중간에 바뀌지 않는다"는 보장이 순전히 개발자의 습관에 의존하게 된다.

(참고: "생성 시점에 의존성이 다 갖춰짐이 보장 안 된다"는 이유도 종종 언급되지만, 실제로 위험한 범위는 좁다 — 아래 5번 참고.)

## 4. 왜 이런 차이가 나는가 — 리플렉션이 개입하는 타이밍

필드 주입과 생성자 주입의 모든 차이는 사실 하나의 구조적 차이에서 파생된다: **리플렉션이 "생성과 동시에" 개입하느냐, "생성 이후에" 개입하느냐.**

리플렉션은 실행 중인 프로그램이 자기 자신의 클래스 구조(필드/메서드)를 코드로 들여다보고 조작하는 기능이다. `Field.set(객체, 값)` 같은 API는 **이미 존재하는 객체**를 첫 번째 인자로 요구한다 — 없는 객체의 필드에 값을 넣는다는 게 개념적으로 불가능하기 때문이다. 그래서 필드 주입은 논리적으로 반드시 두 단계로 쪼개진다.

스프링 내부 흐름(단순화):

```java
1. createBeanInstance()
   → new OrderService()  // 기본 생성자로 빈 객체 생성. 이 시점 필드는 아직 미주입

2. populateBean()
   → clazz.getDeclaredFields() 순회  // 문자열로 이름을 찾는 게 아니라, 선언된 필드 전부를 나열
   → @Autowired 붙은 필드만 골라냄 (isAnnotationPresent)
   → field.set(객체, 값)  // 리플렉션으로 강제 주입
```

생성자 주입은 이 과정이 하나로 합쳐진다:

```java
1. 생성자 파라미터 타입을 먼저 파악해 의존성을 준비
2. new OrderService(paymentClient빈)  // 생성 = 주입, 중간 상태 자체가 없음
```

이 타이밍 차이가 필드 주입의 단점들을 만든다. 다만 정확히 어디까지 영향을 미치는지는 구분해야 한다:

- `final` 불가: 리플렉션으로 생성자 밖에서 나중에 대입하는 구조라서 문법적으로 `final`과 안 맞음 — 이건 항상 유효한 차이.
- 순환 참조 우회: 1단계(생성)에서는 서로를 몰라도 되므로(기본 생성자만 부르면 됨) 순환을 넘어갈 수 있음 — 이것도 항상 유효.
- 테스트 시 스프링 필요: 2단계(주입)를 실행해줄 주체가 컨테이너뿐이라 — 이것도 항상 유효.

## 5. 정정: "null일 수 있다"는 위험의 정확한 범위

앱이 완전히 뜬 뒤, 실제로 요청을 처리하는 시점에는 모든 빈이 이미 주입 완료된 상태다. 스프링 컨테이너는 1~2단계(생성 → 주입)를 모든 빈에 대해 앱 시작 시점에 한 번에 끝내놓고, 그 다음에야 요청을 받기 시작한다. 그래서 "운영 중에 필드가 null이라 NPE가 난다"는 일은 정상적인 흐름에서는 일어나지 않는다.

진짜 null이 발생할 수 있는 유일한 지점은 **생성자 코드 내부**다:

```java
class OrderService {
    @Autowired
    private PaymentClient paymentClient;

    OrderService() {
        paymentClient.pay(); // NPE — 생성자 실행 시점엔 아직 필드 주입 전(1단계는 끝났지만 2단계 전)
    }
}
```

즉 "필드 주입은 생성 시점에 의존성이 안 갖춰질 수 있다"는 말은, 정확히는 "생성자 코드 안에서 그 필드를 쓰면 안 된다"는 좁은 제약으로 이해하는 게 맞다. 이 위험을 필드 주입 반대 논리의 핵심으로 내세우기보다, 테스트 용이성·순환 참조 조기 발견을 앞세우는 게 더 정확하고 설득력 있다.

## 6. 리플렉션 자체는 실무 코드에 안 나온다

`getDeclaredFields()`, `field.set()` 같은 리플렉션 코드는 스프링 프레임워크 내부(`AutowiredAnnotationBeanPostProcessor`)에 이미 구현돼 있고, 애플리케이션 개발자는 절대 직접 작성하지 않는다. `@Autowired` 어노테이션만 붙이면, 그 뒤의 스캔·주입 과정은 프레임워크가 앱 시작 시점에 자동으로 처리한다. 이 전체 과정은 서버가 뜰 때 딱 한 번 일어나고, 요청마다 반복되지 않는다(스프링 빈은 기본이 싱글톤이므로).

## 한 줄 요약

IoC는 객체 생성/조립의 제어권을 외부로 넘기는 원칙, DI는 그걸 구현하는 기법이고, 생성자 주입이 권장되는 이유는 리플렉션이 "생성과 동시에" 개입해 중간 상태 없이 완전한 객체를 만들기 때문 — 그 결과로 테스트 용이성, 순환 참조 조기 발견, `final`을 통한 불변성 보장이라는 세 가지 실질적 이득을 얻는다.
