## 클러스터드 인덱스 vs 보조 인덱스

| | 클러스터드 인덱스 | 보조 인덱스 |
|---|---|---|
| 생성 시점 | 테이블 생성 시 PK 기준 자동 생성 | `CREATE INDEX`로 직접 생성 |
| 리프 노드 내용 | row 전체 데이터 | 인덱스 건 컬럼 값 + PK 값 |
| 테이블과의 관계 | 테이블의 저장 구조 자체 | 별도의 작은 트리 |
| 조회 시 | 바로 row 전체 확보 | PK를 찾은 뒤 클러스터드 인덱스로 재조회(테이블 룩업) 필요 |

- InnoDB는 테이블을 생성하면 PK 기준으로 클러스터드 인덱스가 자동 생성되며, 이건 별도 인덱스가 아니라 테이블의 저장 구조 자체다.
- 보조 인덱스로 조회할 때: 보조 인덱스에서 조건에 맞는 PK 값을 먼저 찾고 → 그 PK로 클러스터드 인덱스를 한 번 더 타서 실제 row를 가져온다. 이 2단계 접근을 **테이블 룩업**이라 부른다.

## 커버링 인덱스(Covering Index)

- 쿼리가 필요로 하는 모든 컬럼(`SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, `JOIN ON` 등 어디에 등장하든)이 **그 인덱스 안에 이미 다 포함**되어 있으면, 테이블 룩업 없이 보조 인덱스만 읽고 끝낼 수 있다 — 이걸 커버링 인덱스라 부른다.
- "커버링"은 쿼리 하나하나에 대해 성립 여부가 갈리는 개념이다(인덱스 자체가 어떤 쿼리는 커버하고 어떤 쿼리는 못 커버할 수 있음). 이름은 "인덱스가 쿼리 요구를 커버한다"는 뜻에서, 인덱스 쪽 관점으로 붙었다.
- 컬럼에 함수를 씌우면(`WHERE UPPER(name) = 'X'`) 그 컬럼이 인덱스에 있어도 온전히 활용 못 한다(커버링과 별개 문제).

## 복합 인덱스(Composite Index) 컬럼 순서

- 복합 인덱스 `(a, b, c)`는 `a` 기준으로 먼저 정렬, 같은 `a` 안에서 `b`로 정렬, 같은 `a,b` 안에서 `c`로 정렬된 구조다.
- **Leftmost Prefix 원칙**: `a`, `a+b`, `a+b+c` 조건에는 인덱스가 유효하지만, `b`만 단독으로 걸린 조건에는 사용 불가(비효율).
- **등치(`=`) 조건 컬럼을 범위(`>`, `BETWEEN`) 조건 컬럼보다 앞에 둬야 한다.** 이유: 범위 조건 컬럼 뒤에 오는 컬럼은 전역 정렬이 보장되지 않아 인덱스 탐색(seek)이 아니라 훑으며 걸러내는 필터로 전락한다.
  - 예: 인덱스 `(a, b)`에서 `a`는 전체 정렬되지만, `a`가 바뀔 때마다 `b`는 다시 처음부터 정렬되므로 `b`는 전역적으로 정렬되어 있지 않다.
  - `WHERE a > 1 AND b = 5`: `a` 범위는 탐색으로 좁혀지지만, 그 범위 안에서 `b = 5`는 하나씩 훑어야 함(필터).
  - 인덱스를 `(b, a)`로 바꾸면: `b = 5`로 바로 seek → 그 그룹 안에서 `a`가 이미 정렬되어 있으므로 `a`의 범위 조건도 seek+scan으로 처리 가능.
- 동률(둘 다 등치 조건으로 같이 쓰임)일 때만 **선택도 높은 컬럼을 앞에** 두는 게 3순위 기준으로 적용된다. 극단적으로 선택도 높은 컬럼(예: email)은 대개 단독 조건으로 쓰여 애초에 복합 인덱스 논의 대상이 아닌 경우가 많다.
- 예외: `ORDER BY` 요구사항이 있으면 정렬 컬럼이 뒤에 오는 배치가 우선될 수 있고, 등치 컬럼의 선택도가 지나치게 낮으면(예: 값 2종류, 99% 쏠림) 범위 컬럼을 앞에 두는 게 나을 수도 있다.

## 인덱스 순서와 ORDER BY의 관계(filesort)

- 인덱스의 물리적 정렬 순서는 고정이고 쿼리와 무관하다. 다만 어떤 쿼리의 조건/정렬 요구가 그 고정된 정렬 순서와 우연히 일치하면, DB는 추가 정렬 없이 인덱스가 내보내는 순서를 그대로 결과로 쓸 수 있다.
- 예: 인덱스 `(b, a)`에서 `WHERE b=2 ORDER BY a` → `b=2` 그룹 안 `a`가 이미 정렬되어 있어 그대로 활용, 별도 정렬 불필요.
- 반대로 인덱스가 내보내는 순서(예: `a` 기준)와 쿼리가 원하는 정렬(예: `b` 기준)이 다르면, 조건에 맞는 row를 전부 모은 뒤 별도로 재정렬(filesort)해야 한다. `EXPLAIN`의 `Extra` 컬럼에 `Using filesort`로 표시된다.
- 스토리지 엔진(인덱스)은 자신의 고정된 순서대로 row를 하나씩 흘려보낼 뿐이고, 실행기가 그 순서를 그대로 믿고 쓸지 재정렬할지를 실행 계획 단계에서 미리 결정한다.

## B-Tree vs B+Tree

| | B-Tree | B+Tree |
|---|---|---|
| 중간 노드 저장 내용 | 키 + 데이터(포인터) | 키 + 자식 포인터만 |
| 항목 크기 | 큼 | 작음(가벼움) |
| 페이지당 담기는 키 수(Fan-out) | 적음 | 많음 |
| 리프 노드 간 연결 | 없음 | 연결 리스트로 연결 |
| 범위 검색 | 트리를 오르내리며 탐색 | 리프를 옆으로 순회만 하면 됨 |
| 검색 시간 | 중간에서 찾아질 수 있어 들쭉날쭉 | 항상 리프까지 내려가 일정함 |

- **Fan-out과 트리 높이의 관계**: 트리 한 레벨을 내려갈 때마다 페이지(노드) 하나를 읽어야 하므로, 트리 높이 = 탐색에 필요한 디스크 I/O(또는 버퍼풀 접근) 횟수. Fan-out이 클수록 같은 데이터량을 담는 데 필요한 높이가 낮아지고, 그만큼 I/O가 줄어든다.
- InnoDB가 B+Tree를 쓰는 이유: (1) 리프 연결 덕분에 범위 검색이 빠름 (2) Fan-out이 커서 트리 높이가 낮음 → I/O 감소 (3) 항상 리프까지 내려가므로 검색 성능이 일정하고 예측 가능함.

## 쿼리 옵티마이저의 인덱스 선택

- InnoDB는 테이블/인덱스별 통계 정보(row 수, 카디널리티 등)를 갖고 있고, 쿼리마다 사용 가능한 인덱스 후보들의 예상 비용(스캔 예상 row 수, 랜덤 I/O 등)을 계산해 **가장 비용이 낮은 실행 계획**을 선택한다(비용 기반 옵티마이저).
- `EXPLAIN`으로 어떤 인덱스를 탔는지(`key`), 예상 스캔 row 수(`rows`), 접근 방식(`type`: `ALL`=풀스캔 등), 추가 작업 여부(`Extra`: `Using filesort` 등)를 확인할 수 있다.
- 통계가 오래되면 잘못된 선택을 할 수 있어 `ANALYZE TABLE`로 갱신 가능.

## 카디널리티 / 선택도

- **카디널리티**: 컬럼에 존재하는 서로 다른 값의 개수(예: `gender`는 낮음, `email`은 높음).
- **선택도**: 조건을 걸었을 때 전체 row 중 걸러지는 비율. 카디널리티와 사실상 같은 개념을 다른 각도로 표현.
- 선택도가 낮은 컬럼은 인덱스를 걸어도 걸러지는 row가 적어 오히려 랜덤 I/O 비용 때문에 풀스캔보다 느릴 수 있어, 옵티마이저가 인덱스를 무시하고 풀스캔을 택하기도 한다.

## 인덱스 없이 잠금 읽기/UPDATE/DELETE를 하면

- 조건 컬럼에 인덱스가 없으면 클러스터드 인덱스(PK) 전체를 순차 스캔해야 하고, `SELECT ... FOR UPDATE`/`UPDATE`/`DELETE`는 스캔 중 지나가는 모든 row에 일단 락을 걸고 나서 필터링하기 때문에, 조건과 무관하게 테이블 전체 row가 잠기는 결과가 된다.
- 인덱스로 탐색하는 경우: B+Tree 내부 노드를 타고 내려가는 과정은 데이터 row가 아니라 트리 구조를 거치는 것이라 락이 안 걸리고, 최종적으로 도달한 조건에 맞는(또는 범위 안의) row에만 락이 걸린다.

## 인덱스 설계의 실무 기준

- "완벽한 최적화"라는 절대 기준은 없고, 목표 응답 시간(SLA) 충족 + 인덱스 추가에 따른 쓰기 비용/저장 공간 트레이드오프 + 쿼리의 실행 빈도·중요도(비즈니스 우선순위)를 함께 고려해서 "충분하다"고 판단되는 지점에서 멈춘다.
- 인덱스는 읽기를 빠르게 하지만 모든 INSERT/UPDATE/DELETE마다 갱신 비용이 들기 때문에, 쓰기가 잦은 테이블에는 신중하게 추가해야 한다.
