모릭을 배포하고 나서 한동안은 서버 로그를 습관적으로 열어보곤 했습니다. 별일 없으면 창을 닫고, 뭔가 이상해 보이면 뒤져보는 식이었습니다.

그러다 어느 순간 깨달았습니다. 로그를 열어보지 않는 시간에는, 무슨 일이 일어나고 있는지 저 자신도 전혀 알 수 없다는 사실이었습니다.

이 글은 그 깨달음부터 실제로 파이프라인을 만들기까지의 과정을 순서대로 정리한 기록입니다.

## 1. 사용자 제보에 의존하고 있었다는 걸 인정하기

처음엔 이게 큰 문제라고 생각하지 않았습니다. "가끔 로그 보면 되지"라고 넘겼습니다.

그런데 되짚어보니 실제 대응 흐름은 이랬습니다.

```
장애 발생 → (아무도 모름) → 사용자가 불편을 겪음
    → 사용자가 제보 → 그제서야 로그 확인 → 원인 파악 → 대응
```

이걸 글로 써놓고 보니 장애 감지를 사실상 사용자에게 떠넘기고 있었던 셈이었습니다. 제보가 안 오면 문제가 없는 게 아니라, 그저 인지하지 못하고 있는 상태였을 뿐입니다.

그래서 목표를 단순하게 잡았습니다. 사용자가 알려주기 전에 먼저 알 것.

## 2. 뭘 만들어야 할지부터 고민이었다

"그냥 에러 나면 알림 오게 하면 되겠지"라고 쉽게 생각했는데, 막상 뜯어보니 결이 다른 요구가 섞여 있었습니다. 하나는 지금 당장 터진 심각한 에러를 즉시 아는 것이었고, 다른 하나는 하나하나는 심각하지 않아도 자꾸 반복되는 패턴을 놓치지 않는 것이었습니다.

실시간 알림만 만들면 첫 번째는 되지만 두 번째는 안 됩니다. 빈도 낮은 에러는 알림이 뜨더라도 그냥 넘기기 쉽기 때문입니다.

그래서 두 층위로 나눠서 만들기로 했습니다. 실시간 알림 하나, 주기적으로 상태를 요약해주는 리포트 하나.

도착할 곳은 고민할 것도 없이 Discord였습니다. 개발할 때 항상 켜두는 채널이었으니까요.

새로운 대시보드를 하나 더 만들어서 "가끔 확인하는 곳"을 늘리기보다, 이미 보고 있는 곳으로 알림이 오게 하는 게 맞다고 판단했습니다.

## 3. 로그를 새로 쌓기보다, 이미 있는 걸 활용하자

알림 시스템을 만든다고 하면 "로깅 시스템을 새로 짜야 하나" 싶었는데, 곰곰이 생각해보니 그럴 필요가 없었습니다. Cloud Run은 이미 로그를 남기고 있었기 때문입니다.

문제는 그 로그를 아무도 실시간으로 보고 있지 않다는 것뿐이었습니다. 그래서 GCP의 로그 인프라를 그대로 타고 가는 구조로 잡았습니다.

```
Cloud Run (프론트엔드, 백엔드, AI 서버)
    → severity >= ERROR 로그 발생
    → GCP Log Router Sink가 필터링
    → Pub/Sub으로 전달
    → Cloud Function(Gen2)이 트리거
    → 로그 분석
    → Discord Webhook 전송
```

이 방식의 제일 마음에 들었던 점은, 서비스 코드에 알림 로직을 따로 심지 않아도 된다는 것이었습니다. 프론트엔드, 백엔드, AI 서버가 각자 알림을 보내게 만드는 게 아니라, 로그가 이미 흐르고 있는 길목에서 낚아채는 구조라 세 서비스를 한 번에 커버할 수 있었습니다.

Pub/Sub 뒤에는 역할을 나눠서 Cloud Function 두 개를 뒀습니다.

## 4. 에러가 뜨자마자: 실시간 알림 함수

처음 알림을 받아봤을 때는 그냥 "에러 발생"이라는 문구만 떴는데, 막상 받아보니 별로 쓸모가 없다는 걸 바로 느꼈습니다. 에러가 떴다는 걸 아는 것과, 그게 무슨 에러인지 대충이라도 감이 오는 건 완전히 다른 얘기였습니다.

그래서 로그 안의 키워드(`ECONNRESET`, `TimeoutError`, `403` 등)를 매칭해서 11종의 대표 원인으로 자동 분류하도록 만들었습니다. 발생 시각(KST), 서비스명, 원본 로그, 바로 확인할 수 있는 GCP Console 로그 링크까지 같이 보내게 했습니다.

알림을 받고 나서 다시 콘솔로 가서 로그를 검색하는 그 몇 분이 아깝다고 느꼈기 때문입니다.

## 5. 실시간만으로는 놓치는 것들: 정기 리포트 함수

실시간 알림을 붙이고 나서 한동안은 이걸로 충분하다고 생각했습니다. 근데 며칠 지나고 보니, 알림이 하나씩 뜰 때는 "이번만 그런가보다" 하고 넘기게 되는 에러들이 있었습니다.

근데 그게 하루에 몇 번씩 반복되고 있었던 걸 나중에야 알아챘습니다.

그래서 Cloud Scheduler로 3시간마다(하루 8회) 최근 발생한 에러 건수를 집계해서 요약 보고하는 함수를 따로 만들었습니다.

실시간 알림이 "지금 뭐가 터졌는지"를 알려준다면, 이 리포트는 "요즘 자꾸 반복되는 게 뭔지"를 보여주는 역할입니다.

## 6. 만드는 중에 두 번 발목을 잡혔다

**권한 문제**: 처음 배포했을 때 `PERMISSION_DENIED: logging.logEntries.list`부터 만났습니다. 함수가 로그를 조회할 권한이 아예 없었던 것이었습니다. 서비스 계정에 `roles/logging.viewer`, `roles/run.invoker` 권한을 붙여주고서야 넘어갔습니다.

**함수 시그니처 오류**: 그다음엔 `TypeError: notify_discord() takes 1 positional argument but 2 were given`이 떴습니다. 처음엔 코드가 잘못됐나 했는데, 찾아보니 Cloud Functions Gen2에서 Pub/Sub 트리거가 인자를 넘기는 방식 자체가 이전 세대와 달라져 있었습니다. `@functions_framework.cloud_event` 데코레이터로 표준 인터페이스를 맞추고 나서야 해결됐습니다.

둘 다 큰 장애는 아니었는데, 만들면서 든 생각이 있었습니다. 알림 시스템 자체가 조용히 죽어 있으면, 그건 알림이 없는 것보다 더 나쁠 수도 있겠다는 것이었습니다.

있는 줄 알고 안심하고 있는데 실제로는 안 울리고 있는 상황이 제일 무섭습니다.

## 7. 달라진 것

- 이제는 사용자 문의가 오기 전에 Discord로 먼저 장애 상황을 확인합니다.
- 자동 분류 덕분에 에러가 뜨면 로그를 처음부터 뒤지지 않고도 원인을 대략 가늠할 수 있게 됐습니다.
- 3시간 리포트 덕분에, 하나씩 보면 대수롭지 않아 보였던 에러가 사실 반복되고 있었다는 걸 놓치지 않고 잡아냅니다.

## 8. 회고

이 작업을 하기 전에는 배포하고 나면 할 일이 끝난다고 생각했던 것 같습니다.

근데 실제로는 배포 이후의 시간이 훨씬 깁니다. 그 시간 동안 뭔가 잘못되고 있다는 걸 제가 먼저 알아채느냐, 사용자가 알려줄 때까지 모르고 있느냐.

이 차이가 작은 이슈와 큰 장애를 가른다는 걸 이번에 몸으로 느꼈습니다.

거창한 모니터링 시스템을 만든 건 아니었습니다. 그냥 이미 보고 있는 곳으로, 먼저 알아야 할 것들이 오게 만들었을 뿐입니다.

근데 그 단순한 변화가 장애 인지 속도를 결정적으로 바꿨습니다.
