## 들어가며

모릭을 배포하고 나서 한동안은 서버 로그를 습관적으로 열어보곤 했습니다. 별일 없으면 창을 닫고, 뭔가 이상해 보이면 뒤져보는 식이었습니다. 그런데 어느 순간 깨달았습니다. 로그를 열어보지 않는 시간에는, 무슨 일이 일어나고 있는지 저 자신도 전혀 알 수 없다는 사실이었습니다.

## 문제 상황

Cloud Run은 이미 로그를 남기고 있었습니다. 문제는 그 로그를 실시간으로 보고 있는 사람이 아무도 없었다는 점이었습니다. 실제 대응 흐름은 다음과 같았습니다.

```
장애 발생 → (아무도 모름) → 사용자가 불편을 겪음
    → 사용자가 제보 → 그제서야 로그 확인 → 원인 파악 → 대응
```

사용자가 "분석이 안 돼요"라고 문의를 남긴 뒤에야 로그를 확인한 경우가 여러 번 있었습니다. 문의가 오지 않았다면 장애가 없었던 것이 아니라, 그저 인지하지 못하고 있었을 뿐이었습니다. 장애 감지를 사실상 사용자 제보에 의존하고 있는 구조였습니다.

## 원인 분석

원인은 단순했습니다. 로그는 쌓이고 있었지만 그 로그를 확인하는 시점이 정해져 있지 않았습니다. 개발자가 습관적으로 로그를 열어보는 시간에만 문제가 드러났고, 그 사이에 발생한 장애는 사용자가 직접 알려주기 전까지 아무도 모르는 상태로 방치됐습니다.

여기에는 서로 다른 두 가지 요구가 섞여 있었습니다. 하나는 지금 당장 터진 심각한 에러를 즉시 아는 것이었고, 다른 하나는 하나하나는 심각하지 않아도 반복되는 패턴을 놓치지 않는 것이었습니다. 실시간 알림만으로는 두 번째 요구가 채워지지 않습니다. 빈도가 낮은 에러는 알림이 뜨더라도 "이번만 그런가 보다"하고 넘기기 쉽기 때문입니다.

## 재설계

새로운 로깅 시스템을 만드는 대신, GCP가 이미 쌓고 있는 로그 인프라를 그대로 활용하는 경로를 선택했습니다.

```
Cloud Run (프론트엔드, 백엔드, AI 서버)
    → severity >= ERROR 로그 발생
    → GCP Log Router Sink가 필터링
    → Pub/Sub으로 전달
    → Cloud Function(Gen2)이 트리거
    → 로그 분석
    → Discord Webhook 전송
```

이 구조를 선택한 이유는 서비스 코드에 알림 로직을 따로 심지 않아도 됐기 때문입니다. 프론트엔드, 백엔드, AI 서버 각각에 알림 코드를 추가하는 대신, 로그가 이미 흐르는 길목에서 가로채는 방식으로 세 서비스를 한 번에 커버할 수 있었습니다.

앞서 확인한 두 가지 요구에 맞춰 Cloud Function을 역할별로 나눴습니다.

**실시간 알림 함수**: 로그 안의 키워드(`ECONNRESET`, `TimeoutError`, `403` 등)를 매칭해 11종의 대표 원인으로 자동 분류하고, 발생 시각(KST)·서비스명·원본 로그·GCP Console 로그 링크를 함께 전송하도록 구성했습니다. 단순히 "에러 발생"만 알리면 다시 콘솔에서 로그를 검색해야 하는 시간이 그대로 남기 때문입니다.

**정기 리포트 함수**: Cloud Scheduler로 3시간마다(하루 8회) 최근 발생한 에러 건수를 집계해 요약하는 함수를 별도로 만들었습니다. 실시간 알림을 붙이고 나서 한동안은 이걸로 충분하다고 생각했지만, 며칠 지나고 보니 알림이 하나씩 뜰 때는 "이번만 그런가보다" 하고 넘기게 되는 에러들이 하루에 몇 번씩 반복되고 있다는 걸 나중에야 알아챘습니다. 실시간 알림이 "지금 뭐가 터졌는지"를 알려준다면, 이 리포트는 "요즘 자꾸 반복되는 게 뭔지"를 보여주는 역할입니다.

## 엣지 케이스

구현 과정에서 두 가지 문제를 마주쳤습니다.

**권한 문제**: 처음 배포했을 때 `PERMISSION_DENIED: logging.logEntries.list`부터 만났습니다. 함수가 로그를 조회할 권한이 아예 없었던 것이었고, 서비스 계정에 `roles/logging.viewer`, `roles/run.invoker` 권한을 부여한 뒤 해결했습니다.

**함수 시그니처 오류**: 그다음엔 `TypeError: notify_discord() takes 1 positional argument but 2 were given`이 발생했습니다. 처음엔 코드가 잘못됐나 싶었지만, 찾아보니 Cloud Functions Gen2에서 Pub/Sub 트리거가 인자를 넘기는 방식 자체가 이전 세대와 달라져 있었습니다. `@functions_framework.cloud_event` 데코레이터로 표준 인터페이스를 맞추고 나서야 해결됐습니다.

둘 다 큰 장애는 아니었지만, 만들면서 든 생각이 있었습니다. 알림 시스템 자체가 조용히 죽어 있으면, 그건 알림이 없는 것보다 더 나쁠 수도 있다는 것이었습니다. 있는 줄 알고 안심하고 있는데 실제로는 울리지 않고 있는 상황이 가장 위험합니다.

## 결과 및 회고

이제는 사용자 문의가 오기 전에 Discord로 먼저 장애 상황을 확인합니다. 자동 분류 덕분에 로그를 처음부터 뒤지지 않고도 원인을 대략 가늠할 수 있고, 3시간 리포트 덕분에 하나씩 보면 대수롭지 않아 보였던 에러가 실제로는 반복되고 있었다는 것도 놓치지 않게 됐습니다.

1. **배포 이후의 시간이 배포 자체보다 훨씬 깁니다.** 그 시간 동안 뭔가 잘못되고 있다는 걸 먼저 알아채느냐, 사용자가 알려줄 때까지 모르고 있느냐의 차이가 작은 이슈와 큰 장애를 가른다는 걸 이번에 체감했습니다.
2. **새로운 모니터링 인프라를 구축한 것이 아니라, 이미 쌓이고 있던 로그가 이미 보고 있는 채널로 흘러오게 만든 것뿐이었지만, 그 단순한 변화가 장애 인지 속도를 결정적으로 바꿨습니다.**
