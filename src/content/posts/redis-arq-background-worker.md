## 들어가며

Cloud Run 같은 서버리스 컨테이너 환경에는 두 가지 상한이 함께 존재합니다. 하나는 인스턴스 하나가 동시에 처리할 수 있는 요청 수의 상한이고, 다른 하나는 요청 하나가 응답을 받기까지 기다릴 수 있는 시간의 상한입니다. 모릭의 초기 아키텍처는 이 두 상한을 모두 요청-응답 경로 안에서 그대로 맞닥뜨리는 구조였습니다.

## 문제 상황

### 부하 테스트로 처음 드러난 동시 처리량의 한계

Grafana와 Prometheus, Locust를 활용해 가상 사용자 100명으로 부하 테스트를 진행한 결과, 실시간 처리 중인 요청 수 그래프가 시스템 임계치인 80을 지속적으로 초과하는 현상이 관측됐습니다. 당시 Cloud Run 설정상 단일 인스턴스가 동시에 처리할 수 있는 최대 요청 수는 80개로 제한돼 있었고, 인프라는 최대 인스턴스 3개 × 인스턴스당 80명 = 총 240명 규모였습니다.

서비스의 핵심 기능인 AI 강의 복습이 평균 15초 이상의 처리 시간을 요구한다는 점이 문제였습니다. 300명이 동시에 접속하면 240명은 정상적으로 서비스를 이용할 수 있지만, 나머지 60명은 처리 슬롯을 기다리며 대기해야 했습니다.

### 대용량 문서에서 드러난 또 다른 상한

동시 처리량 문제와 별개로, 문서 분량이 큰 경우에는 60초의 Gateway 타임아웃 자체를 넘기는 문제가 있었습니다. 초기 아키텍처는 구현을 단순하게 가져가기 위해 클라이언트 요청에 분석 결과를 즉시 반환하는 동기(Synchronous) 방식으로 설계돼 있었고, 문서가 짧을 때는 문제가 없었지만 분량이 늘어나는 순간 60초 제한과 정면으로 부딪혔습니다.

## 원인 분석

### 왜 인스턴스를 늘리는 것만으로는 부족한가

동시 처리량 문제를 풀기 위해 검토한 첫 번째 방법은 인스턴스를 수직·수평으로 확장하는 것이었습니다. 300명을 수용하려면 최소 4개 이상의 인스턴스가 필요했고, 코드 수정 없이 설정 변경만으로 즉시 적용할 수 있다는 장점이 있었습니다. 하지만 사용자가 늘어날 때마다 인스턴스 비용이 선형적으로 증가하고, 15초라는 긴 대기 시간을 유지하는 동기식 구조 자체가 네트워크 불안정에 취약하다는 근본적인 한계는 그대로 남았습니다.

두 번째로 검토한 방법은 처리 시간 자체를 단축하는 것이었습니다. 15초를 1초로 줄일 수 있다면 동일 자원으로 15배 많은 트래픽을 처리할 수 있지만, 병목의 주원인이 외부 Gemini API의 응답 대기 시간이었기 때문에 내부 로직 최적화만으로는 유의미한 개선을 기대하기 어려웠습니다.

### 90페이지라는 확정적인 경계선

동시 처리량 문제를 비동기 구조로 풀기로 방향을 잡은 뒤, 대용량 문서의 타임아웃 문제도 같은 구조 안에서 해결할 수 있는지 검증했습니다. "특정 페이지 수 이상의 문서는 60초 안에 처리가 불가능할 것"이라는 가설을 세우고 다양한 분량의 문서로 반복 테스트를 진행한 결과, 90페이지 이상의 문서에서는 추론 시간이 확정적으로 60초를 넘겨 타임아웃이 우연이 아니라 필연적으로 발생한다는 것을 확인했습니다.

여기에 더해 장애 상황에서 부작용이 하나 더 드러났습니다. 타임아웃이나 에러가 나면 Langchain 자체 재시도 로직과 인프라 레벨 재시도가 동시에 걸리면서, 실패한 요청 하나가 외부 API 호출을 중복으로 증폭시키는 재시도 폭풍(Retry Storm)이 발생했습니다. 이는 다시 429 Rate Limit을 유발해 정상 요청까지 함께 실패시켰습니다.

## 재설계

비동기 아키텍처로 전환하기 위해 두 가지 큐 구현 방식을 비교했습니다.

1. **GCP Cloud Tasks(관리형 큐)**
   - 장점: 인프라 운영 부담이 적고 확장성이 우수합니다.
   - 단점: 로컬 개발 환경 구성이 복잡하고, 로그가 여러 서비스로 분산돼 요청 하나의 전 구간을 추적하기 어려웠습니다.
2. **Redis + ARQ(자가 구축형 큐) — 채택**
   - 장점: 재시도 정책과 타임아웃을 애플리케이션 레벨에서 세밀하게 제어할 수 있고, 로컬과 운영 환경의 동작을 동일하게 맞추기 쉬웠습니다.
   - 단점: Redis 인프라를 직접 관리해야 하는 부담이 있습니다. 디버깅 생산성과 시스템 통제권을 우선순위로 두고 이 부담을 감수했습니다.

```
[클라이언트 요청]
    ↓
[FastAPI: Redis 큐에 작업 등록] ── 즉시 200 응답 (0.1초 내)
    ↓                                (60초 제한 밖으로 이탈)
[ARQ Worker: 백그라운드에서 AI 분석 수행]
    ↓
[Firestore/PostgreSQL에 결과 또는 실패 상태 기록]
```

관리 포인트를 늘리지 않기 위해 하나의 Cloud Run 컨테이너 안에서 FastAPI(Web)와 ARQ Worker(Process)를 함께 띄우는 구조로 설계했습니다. 워커 설정도 동시 처리량 문제의 실측치에 맞춰 조정했습니다. `max_jobs`를 2로 하향해 단일 인스턴스 내 AI 모델 호출 부하를 직접 제어했고, `job_timeout`은 3,600초(60분)로 대폭 상향해 대용량 강의 자료 분석이 워커 내부 타임아웃으로 중단되는 현상을 막았습니다.

원격 Redis와의 연결이 끊기지 않도록 `socket_timeout(60s)`과 `keep-alive`를 강화했고, API 서버와 워커가 같은 요청을 서로 다른 로그로 남기지 않도록 요청 ID를 요청 전 구간에 부여해 하나의 컨텍스트로 묶었습니다. 실패 처리도 함께 다듬어, 어느 단계에서 예외가 나든 `try-except-finally`로 감싸 반드시 실패 상태를 기록하도록 했고, 사용자 입력에 포함된 특수문자(`{}`)가 프롬프트 구문 에러를 유발하지 않도록 Langchain의 `invoke()` 주입 방식으로 바꿨습니다.

프론트엔드에서는 `TaskMonitor` 컴포넌트로 진행률을 보여주되, 진행률이 70% 근처에서 오래 머무는 구간에도 "숨 쉬는" 형태의 인디케이터를 두어 사용자가 멈춘 것으로 오해하지 않도록 다듬었습니다.

## 엣지 케이스: 비동기로 넘긴 뒤에도 남은 문제

작업을 백그라운드로 넘기고 나니, 이번에는 클라이언트 쪽에서 새로운 문제가 나타났습니다. 프론트엔드는 진행률 확인을 위해 일정 주기로 서버 상태를 폴링했는데, 이 폴링은 브라우저 탭이 열려 있을 때만 동작했습니다. 사용자가 분석 요청 후 탭을 닫거나 다른 페이지로 이동하면, ARQ 워커는 클라이언트와 무관하게 계속 처리를 이어가 결과를 정상적으로 저장했지만, 사용자는 완료 시점을 알 방법이 없었습니다. 실제 데이터 유실은 없었는데도 "분석이 취소된 것 아닌가" 하는 불확실성 때문에 재업로드를 시도하는 사용자가 있었습니다.

WebSocket이나 Server-Sent Events로 서버가 완료 시점을 푸시하는 방법, 브라우저 Notification API로 탭이 닫혀도 OS 알림을 보내는 방법도 검토했지만, 전자는 연결이 유지돼야 하므로 탭을 닫으면 같은 문제가 재발했고 후자는 권한 허용이 전제 조건이라 실효성이 불확실했습니다. 대신 폴링을 없애는 대신 사용자가 다시 페이지에 진입하는 시점에 서버 상태를 조회하는 방식을 택했습니다. 작업의 생명주기는 서버(ARQ 워커)가 클라이언트 연결과 무관하게 책임지고, 상태를 언제 확인할지의 타이밍만 클라이언트가 결정하도록 역할을 나눈 것입니다.

## 결과 및 회고

비동기 전환 이후 60초 타임아웃 에러는 발생하지 않았고, 테스트 데이터를 근거로 안정적으로 처리 가능한 상한선을 60페이지로 확정해 시스템에 반영했습니다. 이 구조 위에서 요청 처리 성공률은 97.4%까지 올랐습니다.

1. **"AI 응답을 더 빠르게 만드는 것"이 아니라 "느린 응답을 요청-응답 경로 밖으로 빼내는 것"이 문제 해결의 실제 방향이었습니다.** 인프라의 제약(동시 처리량 80, 타임아웃 60초)은 코드로 없앨 수 없는 조건이었고, 그 조건을 우회하는 구조를 설계하는 것이 더 현실적인 해법이었습니다.
2. **가설을 먼저 세우고 검증하는 절차가 상한선(60페이지)이라는 구체적인 기준을 만들어줬습니다.** "느릴 수 있다"가 아니라 "90페이지부터는 확정적으로 실패한다"는 데이터가 있었기 때문에, 이후 시스템에 반영할 안전장치의 기준을 임의로 정하지 않을 수 있었습니다.
3. **비동기 전환은 한 번의 구조 변경으로 끝나지 않았습니다.** 서버 쪽 병목을 해소하고 나니 클라이언트의 연결 생명주기라는 다른 층위의 문제가 드러났고, "서버 작업의 생명주기는 서버가, 상태 조회의 타이밍은 클라이언트가" 책임지는 역할 분리가 그 다음 단계의 실제 해법이었습니다.
