사용자가 특정 레벨에 진입할 때마다 학습 세션(`chatbot_study_status`)을 생성하는 기능이 있습니다. 비즈니스 규칙상 사용자는 동일 레벨에서 진행 중(`status=1`) 세션을 단 하나만 가질 수 있고, 완료·취소된 세션(`status=2,3`)은 학습 이력으로 계속 쌓여야 합니다.

> 인덱스 하나 추가한다고 "느린 쿼리를 빠르게" 만든 게 아니었습니다. 그 인덱스가 실제로 바꾼 건 락이 걸리는 범위였습니다. 그리고 범위를 다 좁힌 뒤에도, 락이 걸리는 순서라는 별개의 문제가 남아있었습니다.

500 VUs 동시 요청 기준 p95 응답 지연이 8.86초까지 치솟고 데드락으로 인한 500 에러가 빈번히 발생했던 문제를, 두 단계에 걸쳐 p95 1.45초·데드락 0건까지 개선한 과정입니다.

## 원자적 쿼리로 Race Condition은 잡았는데

세션 생성 로직은 원래 "조회 후 없으면 삽입"하는 흔한 구조였습니다.

```java
Integer ongoingStatusNo = gameMapper.selectOngoingStudyStatus(userNo, ...);
if (ongoingStatusNo != null) return ongoingStatusNo;
gameMapper.insertStudyStatus(status);
```

사용자가 버튼을 연타하면 두 요청이 조회 구간을 동시에 통과해 세션이 중복 생성되는 Race Condition이 있었고, 이를 막기 위해 조건 검사와 삽입을 하나의 원자적 쿼리로 합쳤습니다.

```sql
INSERT INTO chatbot_study_status (user_no, level_title_no, game_type, quiz_type, status)
SELECT #{userNo}, #{levelTitleNo}, #{gameType}, #{quizType}, 1
FROM DUAL
WHERE NOT EXISTS (
    SELECT 1 FROM chatbot_study_status
    WHERE user_no = #{userNo} AND status = 1 ...
);
```

쿼리 하나로 중복은 확실히 막혔습니다. 문제는 이 쿼리를 부하 상황에 올리면서 시작됐습니다.

## 왜 락이 테이블 전체로 번졌나

`WHERE NOT EXISTS`의 서브쿼리가 참조하는 컬럼에는 인덱스가 없었습니다. DB 엔진은 중복 여부를 판별하기 위해 테이블 전체를 훑는 Full Table Scan을 선택했고, `REPEATABLE READ` 격리 수준에서 인덱스 없는 스캔은 스캔 경로에 놓인 모든 레코드와 그 사이 간격(Gap)에 Next-Key Lock을 겁니다.

결과적으로 A 유저의 중복 가입을 막으려던 쿼리가 A 유저와 아무 상관 없는 다른 유저들의 삽입 요청까지 막아버렸습니다. 부하 테스트에서는 특정 유저 하나의 조건 검사가 테이블 전체의 쓰기 처리량을 마비시키는 형태로 나타났고, 관련 없는 유저의 요청이 큐잉 지연을 겪다 연결이 거절되는 현상까지 이어졌습니다.

여기서 확인해야 했던 건 "왜 느린가"가 아니라 "이 쿼리가 락을 거는 범위가 어디까지인가"였습니다. 인덱스가 없는 조건절은 DB 엔진 입장에서 "어디까지가 안전한 범위인지" 판단할 근거가 없기 때문에, 가장 보수적인 선택인 "전체를 잠근다"로 귀결됩니다.

## 세 가지 방법, 그리고 남은 절반의 문제

락 범위를 줄이기 위한 세 가지 방법을 비교했습니다.

1. **Redis 분산 락** — DB 락 승격 규칙과 완전히 독립적으로 동시성을 제어할 수 있지만, 단일 DB로 운영되는 인프라에 새 저장소와 모니터링 체계를 얹는 비용이 이 문제 하나를 풀기엔 과했습니다. 기각했습니다.
2. **일반 복합 유니크 인덱스** — 중복 자체를 스키마 레벨에서 강력하게 막아주지만, "완료된 세션은 무한히 쌓이고 진행 중 세션만 하나여야 한다"는 요구사항과 맞지 않았습니다. 완료 이력이 계속 쌓여야 하는 컬럼 조합에서도 중복이 차단돼, 유저가 같은 레벨을 재학습한 이력을 저장할 수 없게 됩니다. 채택하지 않았습니다.
3. **선택도 기반 복합 인덱스 (채택)** — 조회 조건을 그대로 인덱스로 반영하면서 데이터 모델을 바꾸지 않아도 됩니다. 다만 인덱스 자체가 조건부 유일성(진행 중 세션만 하나)까지 보장해주지는 않으므로, 이 부분은 별도로 처리해야 했습니다.

`WHERE NOT EXISTS`가 참조하는 조건절 순서에 맞춰, 고유값 범위가 가장 넓은 `user_no`를 선두로 하는 복합 인덱스를 구성했습니다.

```sql
CREATE INDEX idx_study_session_check
ON chatbot_study_status (user_no, level_title_no, game_type, quiz_type, status);
```

이 인덱스를 추가한 뒤 실행 계획이 전체 스캔(`ALL`)에서 인덱스 범위 스캔(`ref`)으로 바뀌었고, 락이 걸리는 범위도 테이블 전체에서 특정 `user_no` 근처의 좁은 구간으로 줄었습니다. 다른 유저의 요청이 A 유저의 요청 때문에 대기하는 현상이 사라졌습니다.

## 인덱스가 푼 문제, 인덱스가 못 푼 문제

부하 테스트를 반복하는 과정에서, 락 범위 축소만으로는 사라지지 않는 증상이 하나 남아있었습니다. 같은 유저가 짧은 간격으로 버튼을 두 번 누르면, 간헐적으로 이 예외와 함께 요청 하나가 500 에러로 튕겨 나갔습니다.

```
org.springframework.dao.CannotAcquireLockException:
### Error updating database. Cause: java.sql.SQLException:
Deadlock found when trying to get lock; try restarting transaction
```

인덱스를 추가한 이후 서로 다른 유저 간의 락 경합은 완전히 사라졌습니다. A 유저의 요청이 B 유저의 요청을 막는 일은 더 이상 없었습니다.

하지만 같은 유저가 짧은 시간 안에 요청을 두 번 연달아 보내는 경우, 즉 같은 인덱스 구간을 두 번 건드리는 경우에는 여전히 실패가 발생했습니다. 인덱스로 락 범위를 좁힌 뒤에도 남아있는 문제라는 것은, 원인이 "락이 걸리는 범위"가 아니라 "락이 걸리는 방식" 자체에 있다는 뜻이었습니다.

## 락이 얽히는 순간

`WHERE NOT EXISTS` 조건부 삽입은 이름은 "삽입"이지만, 내부적으로는 여전히 조회가 먼저 실행됩니다. 서브쿼리가 대상 레코드의 존재 여부를 확인하는 순간 InnoDB는 해당 범위에 공유 락(S-Lock)을 겁니다. 조회가 끝나고 실제로 행을 삽입하는 단계에서는, 이 공유 락을 배타 락(X-Lock)으로 승격해야 합니다.

같은 유저의 요청 두 개가 거의 동시에 들어오면, 이 승격 시점에 다음과 같이 락이 얽힙니다.

![락 승격 경합으로 인한 데드락 시퀀스](/diagrams/deadlock-promotion-sequence.png)

두 트랜잭션 모두 "내가 쥔 공유 락을 배타 락으로 승격하고 싶은데, 상대방이 아직 자기 공유 락을 놓지 않고 있다"는 상태에 동시에 빠집니다. 서로가 서로의 락 해제를 기다리는 순환 대기, 즉 데드락입니다.

인덱스는 "락이 걸리는 범위"를 테이블 전체에서 특정 `user_no` 근처로 좁혀주는 역할을 했을 뿐, 같은 유저의 요청끼리 겪는 "조회 먼저, 삽입은 그다음"이라는 승격 순서 문제는 건드리지 못했습니다. 범위(where)와 순서(how)는 서로 다른 층위의 문제였습니다.

## 데드락을 없앨 것인가, 흡수할 것인가

락 승격 경합을 없애기 위한 방법을 세 가지 비교했습니다.

1. **Redis 분산 락** — 애플리케이션 레벨에서 요청 자체를 직렬화할 수 있어, DB 락 메커니즘과 완전히 독립적으로 동시성을 제어할 수 있습니다. 다만 단일 DB로 운영 중인 인프라에 락 서버를 새로 얹어야 하고, 락 서버의 장애나 지연이 곧 세션 생성 API 전체의 장애로 이어질 수 있는 새로운 단일 장애점을 만드는 셈이라 이 문제 하나를 풀기 위해 감수하기엔 운영 비용이 과했습니다. 기각했습니다.
2. **완전한 애플리케이션 레벨 직렬화(동기 락, synchronized)** — 구현이 가장 단순하고 별도 인프라도 필요 없습니다. 하지만 인스턴스가 여러 대로 스케일아웃되는 순간 각 인스턴스가 독립된 JVM 메모리 위에서 락을 걸기 때문에 서로 다른 인스턴스로 분산된 요청끼리는 동시성 제어가 전혀 되지 않습니다. 배제했습니다.
3. **조회 없이 삽입 먼저, 실패 시 재조회 (채택)** — "조회 후 삽입"이라는 순서 자체를 없애기 때문에, 공유 락을 먼저 잡는 단계 자체가 사라집니다. 별도 인프라 없이 기존 DB와 애플리케이션 코드 레벨에서 해결됩니다. 다만 "진행 중 세션은 하나만, 완료 세션은 무한 누적"이라는 조건부 유일성을 스키마 레벨에서 강제할 방법이 별도로 필요했습니다.

세 번째 안을 채택하되, 남은 단점을 MySQL 8.0의 함수형 유니크 인덱스로 해결했습니다.

```sql
ALTER TABLE chatbot_study_status
ADD UNIQUE INDEX uq_active_session_only (
    (CASE WHEN status = 1 THEN user_no ELSE NULL END),
    level_title_no, quiz_type, game_type
);
```

SQL 표준상 `NULL` 값은 유니크 인덱스의 중복 비교 대상에서 제외됩니다. `status = 1`(진행 중)일 때만 유저 번호가 인덱스 키로 매핑되어 중복이 차단되고, 완료 상태(`status = 2, 3`)가 되면 값이 `NULL`로 바뀌어 이력이 제약 없이 계속 쌓일 수 있습니다.

```java
@Override
@Transactional
public Integer startStudySession(StudyStatus status) {
    try {
        // 선조회 없이 즉시 삽입 시도 — 공유 락을 아예 잡지 않는다
        int affectedRows = gameMapper.insertStudyStatusAtomic(status);
        if (affectedRows > 0) {
            return status.getStudyStatusNo();
        }
    } catch (DeadlockLoserDataAccessException | DuplicateKeyException e) {
        log.warn("동시성 경합 감지 -> Fallback 조회 실행. User: {}", status.getUserNo());
    }

    // 충돌한 요청만 뒤늦게 조회해서, 먼저 성공한 세션 ID를 그대로 반환
    return gameMapper.selectOngoingStudyStatus(status.getUserNo(), status.getLevelTitleNo());
}
```

늦게 들어온 요청은 예외를 사용자에게 그대로 노출하는 대신, 먼저 성공한 트랜잭션이 만든 세션 ID를 재조회해 반환합니다. 데드락 자체를 100% 없애려고 애쓰기보다, 발생을 인정하고 실패한 쪽이 안전하게 복구할 수 있는 경로를 만드는 편이 낫다는 판단이었습니다.

`DeadlockLoserDataAccessException`과 `DuplicateKeyException`을 함께 잡는 이유도 여기에 있습니다. 데드락으로 롤백되든, 유니크 인덱스 충돌로 실패하든, 결국 "누군가 먼저 성공했다"는 같은 상황이므로 같은 방식으로 복구합니다. 몇 개의 트랜잭션이 동시에 충돌하든 성공은 정확히 1개만 허용되고 나머지는 전부 같은 Fallback 경로를 타므로, 경합 트랜잭션 수와 무관하게 로직이 그대로 성립합니다.

## 재현 검증

이 구조로 바꾼 뒤 500 VUs 규모의 극한 동시성 부하 테스트로 재검증했습니다. 씽크타임을 0으로 두고 단일 진입점에 500개의 요청을 동시에 쏟아붓는 시나리오였습니다.

```javascript
export const options = {
    scenarios: {
        extreme_concurrency: {
            executor: 'per-vu-iterations',
            vus: 500,
            iterations: 1,       // 각 VU당 딱 1번만 실행 — 동시 진입을 최대화
            maxDuration: '30s',
        },
    },
};
```

확인하고 싶었던 건 응답 속도가 아니라, 500개의 동시 요청이 정확히 1개의 세션만 만들어내는지였습니다. 응답으로 돌아온 `studyStatusNo`를 전부 모아 중복을 제거했을 때 유일한 값이 1개뿐이어야 정상입니다.

한 가지 더 주의를 기울인 지점은 Fallback 조회 자체의 타이밍이었습니다. 삽입에 실패한 요청이 재조회를 시도하는 시점에, 먼저 성공한 트랜잭션이 아직 커밋 전이라면 재조회 역시 빈 결과를 받을 수 있습니다. Fallback 조회 쿼리 자체도 동일 트랜잭션의 격리 수준(`REPEATABLE READ`) 안에서 커밋된 데이터만 읽도록 별도 트랜잭션 경계로 분리해뒀습니다.
