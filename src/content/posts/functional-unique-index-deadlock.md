세션 생성은 겉보기엔 단순한 INSERT 하나입니다. 하지만 "사용자당 진행 중 세션은 하나만 허용하고, 완료된 세션은 학습 이력을 위해 무한히 쌓는다"는 규칙이 붙는 순간, 이 INSERT는 더 이상 단순하지 않습니다. `WHERE NOT EXISTS` 조건부 삽입 쿼리로 중복 세션 생성 자체는 막았고, 복합 인덱스로 락이 걸리는 범위도 특정 유저 단위로 좁혔습니다. 여기까지만 보면 문제가 끝난 것처럼 보였습니다.

## 인덱스가 푼 문제, 인덱스가 못 푼 문제

부하 테스트를 반복하는 과정에서, 락 범위 축소만으로는 사라지지 않는 증상이 하나 남아있었습니다. 같은 유저가 짧은 간격으로 버튼을 두 번 누르면, 간헐적으로 이 예외와 함께 요청 하나가 500 에러로 튕겨 나갔습니다.

```
org.springframework.dao.CannotAcquireLockException:
### Error updating database. Cause: java.sql.SQLException:
Deadlock found when trying to get lock; try restarting transaction
```

인덱스를 추가한 이후 서로 다른 유저 간의 락 경합은 완전히 사라졌습니다. A 유저의 요청이 B 유저의 요청을 막는 일은 더 이상 없었습니다. 하지만 같은 유저가 짧은 시간 안에 요청을 두 번 연달아 보내는 경우, 즉 같은 인덱스 구간을 두 번 건드리는 경우에는 여전히 실패가 발생했습니다. 인덱스로 락 범위를 좁힌 뒤에도 남아있는 문제라는 것은, 원인이 "락이 걸리는 범위"가 아니라 "락이 걸리는 방식" 자체에 있다는 뜻이었습니다.

## 락이 얽히는 순간

`WHERE NOT EXISTS` 조건부 삽입은 이름은 "삽입"이지만, 내부적으로는 여전히 조회가 먼저 실행됩니다. 서브쿼리가 대상 레코드의 존재 여부를 확인하는 순간 InnoDB는 해당 범위에 공유 락(S-Lock)을 겁니다. 조회가 끝나고 실제로 행을 삽입하는 단계에서는, 이 공유 락을 배타 락(X-Lock)으로 승격해야 합니다.

같은 유저의 요청 두 개가 거의 동시에 들어오면, 이 승격 시점에 다음과 같은 순서로 락이 얽혔습니다.

```
트랜잭션 A: WHERE NOT EXISTS 조회 → 공유 락(S-Lock) 획득 (성공)
트랜잭션 B: WHERE NOT EXISTS 조회 → 공유 락(S-Lock) 획득 (성공 — 공유 락끼리는 충돌하지 않는다)
트랜잭션 A: INSERT 실행 → 배타 락(X-Lock)으로 승격 시도 → B의 S-Lock 해제 대기
트랜잭션 B: INSERT 실행 → 배타 락(X-Lock)으로 승격 시도 → A의 S-Lock 해제 대기
```

두 트랜잭션 모두 "내가 쥔 공유 락을 배타 락으로 승격하고 싶은데, 상대방이 아직 자기 공유 락을 놓지 않고 있다"는 상태에 동시에 빠집니다. 서로가 서로의 락 해제를 기다리는 순환 대기, 즉 데드락입니다. 인덱스는 "락이 걸리는 범위"를 테이블 전체에서 특정 `user_no` 근처로 좁혀주는 역할을 했을 뿐, 같은 유저의 요청끼리 겪는 "조회 먼저, 삽입은 그다음"이라는 승격 순서 문제는 건드리지 못했습니다. 범위(where)와 순서(how)는 서로 다른 층위의 문제였습니다.

## 데드락을 없앨 것인가, 흡수할 것인가

락 승격 경합을 없애기 위한 방법을 세 가지 비교했습니다.

1. **Redis 분산 락**
   - 장점: 애플리케이션 레벨에서 요청 자체를 직렬화할 수 있어, DB 락 메커니즘과 완전히 독립적으로 동시성을 제어할 수 있습니다.
   - 단점: 단일 DB로 운영 중인 인프라에 락 서버를 새로 얹어야 합니다. 락 서버의 장애나 지연이 곧 세션 생성 API 전체의 장애로 이어질 수 있는 새로운 단일 장애점을 만드는 셈이고, 이 문제 하나를 풀기 위해 감수하기엔 운영 비용이 과했습니다. 기각했습니다.
2. **완전한 애플리케이션 레벨 직렬화(동기 락, synchronized)**
   - 장점: 구현이 가장 단순합니다. 별도 인프라도 필요 없습니다.
   - 단점: 인스턴스가 여러 대로 스케일아웃되는 순간 각 인스턴스가 독립된 JVM 메모리 위에서 락을 걸기 때문에 서로 다른 인스턴스로 분산된 요청끼리는 동시성 제어가 전혀 되지 않습니다. 배제했습니다.
3. **조회 없이 삽입 먼저, 실패 시 재조회 (채택)**
   - 장점: "조회 후 삽입"이라는 순서 자체를 없애기 때문에, 공유 락을 먼저 잡는 단계 자체가 사라집니다. 별도 인프라 없이 기존 DB와 애플리케이션 코드 레벨에서 해결됩니다.
   - 단점: "진행 중 세션은 하나만, 완료 세션은 무한 누적"이라는 조건부 유일성을 스키마 레벨에서 강제할 방법이 별도로 필요합니다. 일반 유니크 인덱스로는 이 조건을 표현할 수 없습니다.

세 번째 안을 채택하되, 남은 단점을 MySQL 8.0의 함수형 유니크 인덱스로 해결했습니다.

```sql
ALTER TABLE chatbot_study_status
ADD UNIQUE INDEX uq_active_session_only (
    (CASE WHEN status = 1 THEN user_no ELSE NULL END),
    level_title_no, quiz_type, game_type
);
```

SQL 표준상 `NULL` 값은 유니크 인덱스의 중복 비교 대상에서 제외됩니다. `status = 1`(진행 중)일 때만 유저 번호가 인덱스 키로 매핑되어 중복이 차단되고, 완료 상태(`status = 2, 3`)가 되면 값이 `NULL`로 바뀌어 이력이 제약 없이 계속 쌓일 수 있습니다.

```java
@Override
@Transactional
public Integer startStudySession(StudyStatus status) {
    try {
        // 선조회 없이 즉시 삽입 시도 — 공유 락을 아예 잡지 않는다
        int affectedRows = gameMapper.insertStudyStatusAtomic(status);
        if (affectedRows > 0) {
            return status.getStudyStatusNo();
        }
    } catch (DeadlockLoserDataAccessException | DuplicateKeyException e) {
        log.warn("동시성 경합 감지 -> Fallback 조회 실행. User: {}", status.getUserNo());
    }

    // 충돌한 요청만 뒤늦게 조회해서, 먼저 성공한 세션 ID를 그대로 반환
    return gameMapper.selectOngoingStudyStatus(status.getUserNo(), status.getLevelTitleNo());
}
```

늦게 들어온 요청은 예외를 사용자에게 그대로 노출하는 대신, 먼저 성공한 트랜잭션이 만든 세션 ID를 재조회해 반환합니다. 데드락 자체를 100% 없애려고 애쓰기보다, 발생을 인정하고 실패한 쪽이 안전하게 복구할 수 있는 경로를 만드는 편이 낫다는 판단이었습니다. `DeadlockLoserDataAccessException`과 `DuplicateKeyException`을 함께 잡는 이유도 여기에 있습니다. 데드락으로 롤백되든, 유니크 인덱스 충돌로 실패하든, 결국 "누군가 먼저 성공했다"는 같은 상황이므로 같은 방식으로 복구합니다.

## 재현 검증

이 구조로 바꾼 뒤 500 VUs 규모의 극한 동시성 부하 테스트로 재검증했습니다. 씽크타임을 0으로 두고 단일 진입점에 500개의 요청을 동시에 쏟아붓는 시나리오였습니다.

```javascript
export const options = {
    scenarios: {
        extreme_concurrency: {
            executor: 'per-vu-iterations',
            vus: 500,
            iterations: 1,       // 각 VU당 딱 1번만 실행 — 동시 진입을 최대화
            maxDuration: '30s',
        },
    },
};
```

확인하고 싶었던 건 응답 속도가 아니라, 500개의 동시 요청이 정확히 1개의 세션만 만들어내는지였습니다. 응답으로 돌아온 `studyStatusNo`를 전부 모아 중복을 제거했을 때 유일한 값이 1개뿐이어야 정상입니다.

한 가지 더 주의를 기울인 지점은 Fallback 조회 자체의 타이밍이었습니다. 삽입에 실패한 요청이 재조회를 시도하는 시점에, 먼저 성공한 트랜잭션이 아직 커밋 전이라면 재조회 역시 빈 결과를 받을 수 있습니다. Fallback 조회 쿼리 자체도 동일 트랜잭션의 격리 수준(`REPEATABLE READ`) 안에서 커밋된 데이터만 읽도록 별도 트랜잭션 경계로 분리해뒀습니다.

## 결과 및 회고

동일한 500 VUs 부하 테스트에서 측정한 안정성 지표입니다.

| 구분 | 지표 | 개선 전 | 개선 후 |
| --- | --- | --- | --- |
| 안정성 | 데드락 / 500 에러 | 빈번 발생 | 0건 |
| 무결성 | 중복 세션 생성 | 다수 발생 | 0건 |

1. **락 범위를 좁히는 것과 락 승격 순서를 없애는 것은 서로 다른 층위의 문제였습니다.** 두 문제를 하나로 뭉쳐서 보면, 인덱스를 추가한 뒤에도 남는 예외를 엉뚱한 방향으로 다시 조사하게 됩니다.
2. **데드락을 완전히 차단하려는 목표는 종종 더 비싼 해법을 부릅니다.** Redis 분산 락은 승격 경합 자체를 없애준다는 점에서 매력적이었지만, 이 문제 하나를 위해 새로운 단일 장애점을 인프라에 추가하는 비용이 더 컸습니다. "일어나지 않게" 만드는 대신 "일어나도 사용자가 모르게" 만드는 방향으로 목표를 바꾸자 훨씬 저렴한 해법이 나왔습니다.
3. **예외 발생 시의 복구 경로를 설계하는 것도 동시성 제어의 일부입니다.** 예외의 종류를 구분하는 것보다, 그 예외가 의미하는 상태를 파악하고 그에 맞는 복구 경로 하나로 통합하는 것이 더 실용적이었습니다.
