## 문제 인식

에듀템 인턴 기간 중 부하 테스트를 돌리다가, 외부 AI API 호출이 몰리는 구간에서 로그인 같은 핵심 API까지 함께 느려지는 현상을 발견했습니다. 원인을 추적해보니 톰캣의 공용 워커 스레드 풀을 외부 API 호출과 핵심 API 요청이 그대로 나눠 쓰고 있었습니다. 외부 API 응답이 늦어지면 그 요청을 처리하던 스레드가 계속 점유 상태로 남고, 뒤이어 들어온 로그인 요청은 빈 스레드가 없어 대기열에 쌓였습니다.

## 원인 분석

- 스레드 풀이 하나뿐이라 외부 API 대기와 핵심 API 처리가 자원을 경쟁했습니다.
- 부하가 몰리는 시점에는 풀이 가득 차 새 요청이 큐에 쌓이며 대기 시간이 그대로 응답 지연으로 전가됐습니다.
- 이 상태에서는 요청을 더 받아도 처리량이 늘지 않고 대기 시간만 늘어나는, 전형적인 자원 경합에 의한 연쇄 지연이었습니다.

## 의사결정

두 가지를 저울질했습니다.

1. **풀 크기를 키운다** — 임시방편일 뿐, 트래픽이 더 몰리면 같은 문제가 재발합니다.
2. **용도별로 풀을 분리한다** — 외부 API 전용 풀과 핵심 API 전용 풀을 나눠, 한쪽이 막혀도 다른 쪽 자원을 침범하지 못하게 합니다.

2번을 선택했습니다. 추가로, 외부 API 전용 풀이 가득 찼을 때 요청을 대기열에 쌓아두지 않고 즉시 거절(Fail-fast)하도록 했습니다. 대기시켜봐야 어차피 타임아웃될 요청이라면, 빨리 실패시켜 클라이언트가 재시도하게 하는 편이 시스템 전체에 유리하다고 판단했습니다.

## 해결

오래 걸리는 API 전용 스레드 풀을 별도로 구성하고, 핵심 API는 기존 풀을 그대로 쓰도록 분리했습니다. 전용 풀에는 큐를 두지 않고 풀이 가득 차면 바로 거절 응답을 내려보내는 정책을 적용했습니다. 이 구조에서는 외부 API 쪽이 아무리 밀려도 핵심 API용 스레드는 절대 잠식되지 않습니다.

## 최종 성과

과부하 상황을 재현한 부하 테스트에서도 핵심 API 지연이 124ms 수준으로 방어됐습니다. 외부 API 쪽 실패는 늘어나지만, 로그인처럼 서비스의 생명선이 되는 요청은 영향을 받지 않는다는 걸 확인했습니다.
