AI 퀴즈 재생성 로직은 기존 문항을 지우고 새 문항을 다시 채우는 구조였습니다. 삭제와 삽입 사이에 실패가 끼면 문항이 통째로 사라질 수 있으니, 이 메서드에 `@Transactional`을 붙여두면 당연히 안전할 거라 생각했습니다.

이 가정이 틀렸다는 걸 알게 된 건, 실제로 삽입이 실패했을 때였습니다.

## 증상: 어노테이션은 있는데 없는 것처럼 동작한다

```java
public class GameServiceImpl {
    @Async
    public void generateQuiz() {
        this.processDbLogic();
    }

    @Transactional
    public void processDbLogic() {
        deleteOldData();
        insertNewData(); // 실패해도 롤백되지 않았다
    }
}
```

삽입 단계에서 예외가 발생했을 때, 롤백이 되어야 할 삭제 작업까지 그대로 커밋돼 퀴즈 테이블이 비어있는 상태로 남는 현상이 발견됐습니다. `@Transactional`은 코드에 분명히 붙어 있었고, 컴파일도 정상적으로 됐고, 다른 화면에서는 같은 어노테이션이 문제없이 동작하고 있었습니다.

그런데 유독 이 메서드에서만 트랜잭션이 마치 처음부터 없었던 것처럼 동작했습니다.

## 프록시가 감시하는 것과 감시하지 못하는 것

Spring의 `@Transactional`은 메서드에 코드를 직접 주입하는 방식이 아닙니다. 대상 빈(Bean)을 감싸는 프록시 객체를 하나 더 만들고, 외부에서 그 빈의 메서드를 호출하면 실제로는 이 프록시가 먼저 호출을 가로챕니다.

프록시는 트랜잭션을 열고, 원본 메서드를 실행하고, 성공하면 커밋, 예외가 나면 롤백한 뒤 호출자에게 결과를 돌려줍니다. `@Transactional`이 동작하는 것처럼 보이는 모든 순간은 사실 이 프록시가 대신 일하고 있는 것입니다.

문제는 `generateQuiz()`가 `processDbLogic()`을 호출하는 방식이었습니다. 두 메서드는 같은 클래스(`GameServiceImpl`)

안에 있었고, 이런 호출은 컴파일된 바이트코드 수준에서 `this.processDbLogic()`과 동일합니다. `this`는 프록시 객체가 아니라 프록시가 감싸고 있는 원본 객체 그 자체를 가리킵니다.

즉 이 호출은 프록시를 거치지 않고 원본 객체 내부에서 바로 실행되며, 프록시가 개입할 기회 자체가 없습니다. `@Transactional` 인터셉터는 프록시 위에만 존재하기 때문에, 원본 객체 내부에서 벌어지는 이 호출에 대해서는 존재하지 않는 것과 같습니다.

여기서 실제로 오해하고 있던 지점이 명확해졌습니다. `@Transactional`이 "메서드 위에 붙어 있으면 항상 동작한다"고 가정했지만, 정확히는 "그 빈의 프록시를 거쳐 호출됐을 때만" 동작합니다.

어노테이션은 선언이고, 프록시를 거치는지는 호출 경로의 문제입니다. 이 둘은 코드를 눈으로 보는 것만으로는 구분되지 않습니다.

## 왜 테스트에서도, 코드 리뷰에서도 걸러지지 않았나

이 버그의 가장 위험한 특징은 조용히 실패한다는 점이었습니다. 컴파일러는 `@Transactional`이 붙은 메서드가 프록시를 거쳐 호출되는지 알 방법이 없어서 아무 경고도 주지 않습니다.

IDE도 마찬가지입니다. 기능 테스트에서도 삭제와 삽입이 둘 다 성공하는 정상 경로만 확인하면 아무 문제가 드러나지 않습니다.

이 문제는 삽입 단계에서 실제로 예외가 발생해야만, 그것도 롤백이 안 됐다는 걸 별도로 확인해야만 드러납니다. 코드만 봐서는 `generateQuiz()`가 `this.processDbLogic()`을 호출하는 게 아니라 `quizGenerationService.processDbLogic()`처럼 다른 빈을 호출하는 것처럼 착각하기 쉬웠던 것도 문제를 더 오래 숨겼습니다.

## 재설계

프록시를 거치도록 만드는 방법을 비교했습니다.

1. **자가 주입(Self-injection)**
   - 장점: 자기 자신을 의존성으로 주입받아 프록시를 통해 호출하는 방식으로, 구현이 간단합니다.
   - 단점: 순환 참조 위험이 있어 설계적으로 지양되는 방식입니다.
2. **TransactionTemplate 직접 사용**
   - 장점: 프로그래밍 방식으로 트랜잭션을 수동 관리하면 프록시 문제 자체에서 자유로워집니다.
   - 단점: 비즈니스 로직에 데이터베이스 관리 코드가 섞여 가독성이 떨어집니다.
3. **트랜잭션 로직을 별도 서비스 빈으로 분리 (채택)**
   - 장점: Spring AOP의 프록시 메커니즘을 자연스럽게 활용할 수 있고, 역할 분리가 명확해집니다.
   - 단점: 클래스가 하나 더 늘어나지만, 이번 사례에서는 이 정도 구조 변경이 가장 근본적인 해결이라고 판단했습니다.

```java
// 1. 트랜잭션 전용 서비스로 로직 이관
public class QuizGenerationServiceImpl implements QuizGenerationService {
    @Transactional
    @Override
    public void processAiQuizGeneration(...) {
        gameMapper.deleteMeaningQuizByUser(...);
        gameMapper.insertMeaningQuizBatch(...); // 실패 시 정상 롤백
    }
}

// 2. 외부 주입을 통한 프록시 호출 유도
public class GameServiceImpl {
    private final QuizGenerationService quizGenerationService;

    @Async
    public void generate_quiz_by_ai(int chatbotReportNo) {
        // 프록시 객체를 통해 호출되므로 트랜잭션이 정상 작동
        quizGenerationService.processAiQuizGeneration(...);
    }
}
```

핵심은 호출 경로를 바꾸는 것이었습니다. `generateQuiz()`가 더 이상 `this`로 자기 자신을 호출하지 않고, 스프링 컨테이너가 관리하는 `QuizGenerationService` 빈을 주입받아 그 빈의 메서드를 호출하도록 바꿨습니다.

이 호출은 외부에서 들어오는 호출이므로 반드시 프록시를 거치고, `@Transactional`이 원래 의도한 대로 동작합니다.

## 재발 방지

이 사례 이후로는 트랜잭션이 필요한 로직을 처음부터 별도 서비스로 분리해두는 걸 원칙으로 삼았습니다. 한 클래스 안에 `@Async`나 `@Transactional`이 붙은 메서드와, 그 메서드를 호출하는 다른 메서드가 함께 있으면 항상 이 호출이 `this`를 통한 내부 호출은 아닌지부터 확인하게 됐습니다.

어노테이션 기반 선언적 트랜잭션은 편리하지만, 그 편리함이 프록시라는 보이지 않는 메커니즘 위에 서 있다는 걸 전제로 코드를 짜야 한다는 걸 이번에 체감했습니다.

1. **`@Transactional`을 붙이는 것과 그 트랜잭션이 실제로 동작하는 것은 다른 문제였습니다.**  
   어노테이션 기반 선언적 트랜잭션은 프록시라는 메커니즘 위에서 동작하고, 같은 클래스 내부 호출은 그 메커니즘을 조용히 건너뜁니다.
2. **이 문제는 코드 리뷰만으로는 잡히지 않는 종류였습니다.**  
   클래스 내부 호출인지 외부 호출인지는 어노테이션만 봐서는 구분되지 않기 때문에, 이후로는 트랜잭션이 필요한 로직을 처음부터 별도 서비스로 분리해두는 걸 원칙으로 삼게 됐습니다.
3. **컴파일러도 IDE도 잡아주지 않는 종류의 버그가 있다는 걸 알게 됐습니다.**  
   프레임워크가 제공하는 편의 기능일수록, 그 기능이 어떤 전제 위에서 동작하는지를 이해하지 않으면 겉으로는 완벽해 보이는 코드가 조용히 실패할 수 있습니다.
