## 들어가며

모릭의 크레딧 차감이 "AI 워커가 분석을 마친 뒤" 이뤄지는 후불제 구조인 데에는 이유가 있었습니다. 원래는 결과 저장과 크레딧 차감이 클라이언트(프론트엔드)에서 각각 별도로 Firestore에 쓰는 구조였는데, 네트워크 불안정이나 탭 종료가 겹치면 결과만 저장되고 차감은 안 되거나, 반대로 차감만 되고 결과는 유실되는 정합성 문제가 있었습니다. AI 분석을 실제로 수행하는 주체가 결과 저장과 크레딧 차감까지 하나의 트랜잭션으로 함께 책임져야 한다는 판단 아래, 이 로직을 워커 내부로 옮기고 멱등성 체크(이미 `completed` 상태면 재처리하지 않음)까지 추가해 원자성 문제를 해결했습니다. 크레딧이 "분석 완료 후"에 차감되는 지금의 구조는 그 개선의 결과물이었습니다.

## 문제 상황

그런데 이 구조를 정리하고 나서 다른 종류의 문제가 드러났습니다. 크레딧 차감이 AI 워커에서 비동기로 처리되는 이상, 요청이 접수된 시점과 실제로 차감이 반영되는 시점 사이에는 필연적으로 지연 구간이 존재합니다. 크레딧이 5개 남은 사용자가 이 지연 구간 안에서 6번 이상 연속으로 요청을 보내면, 앞선 요청들의 차감이 아직 반영되지 않았기 때문에 뒤따르는 요청들도 프론트엔드의 잔여 크레딧 체크를 모두 통과했습니다. 그 결과 DB 데이터가 마이너스로 내려가는 부정합과, 크레딧이 없는데도 AI 분석이 계속 실행되는 서버 자원 낭비(Overdraft)가 함께 발생했습니다.

## 원인 분석

이 문제는 악의적인 공격이 아니라 정상적인 UI 조작(연타)만으로도 재현됐습니다. 앞서 크레딧 차감을 워커 트랜잭션으로 옮긴 결정은 "결과와 차감을 원자적으로 묶는다"는 정합성 문제를 정확히 해결했지만, 그 대가로 "차감 시점이 분석 완료 이후로 미뤄진다"는 새로운 성격의 지연 구간을 만들었습니다. 즉 이번 문제는 이전 개선이 실패해서가 아니라, 그 개선이 만들어낸 정상적인 부작용에 가까웠습니다. "분석 완료 후 차감"이라는 순서 자체가, 차감이 반영되기 전까지의 짧은 시간 동안 잔여 크레딧 체크를 무의미하게 만드는 공백을 구조적으로 내포하고 있었습니다.

## 재설계

정확한 잔여량을 서버와 매 요청마다 동기적으로 확정하는 예약 시스템도 검토했지만, 구현 복잡도가 이 문제의 크기에 비해 컸습니다. 대신 다음 방식을 선택했습니다.

- **프론트엔드**: 버튼 클릭 즉시 UI 상의 크레딧을 먼저 차감(낙관적 차감)해, 다음 클릭이 곧바로 남은 크레딧 부족으로 막히도록 했습니다.
- **AI 백엔드**: 작업이 실패하면 그 시점에 환불 API를 호출해 차감분을 되돌립니다.

```java
// MemberRestController.java — 환불 API
@PostMapping("/usage/refund")
public ApiResponse<Void> refundUsageCount(@Valid @RequestBody RefundUsageRequest request) {
    memberCommandUseCase.refundUsageCount(request.getUid(), request.getTaskId());
    return ApiResponse.onSuccess(null);
}
```

성공 시에는 별도의 차감 API를 호출하지 않습니다. 프론트엔드가 클릭 시점에 이미 차감을 반영했기 때문입니다. 이 방식은 서버와 동기적으로 잔여량을 확정하는 예약 시스템보다 구현이 단순하면서도, 연타로 인한 타이밍 공백은 그대로 막아줍니다. 크레딧 차감과 결과 저장의 원자성을 지키는 역할은 여전히 워커 트랜잭션이 담당하고, 낙관적 차감은 그 트랜잭션이 완료되기 전까지의 UI 반응성만 담당하도록 두 메커니즘의 책임을 분리했습니다.

## 엣지 케이스

낙관적 차감을 도입한 뒤에도 여전히 남는 한계는 있습니다. 프론트엔드가 먼저 차감을 반영하고 서버 응답을 기다리는 구조이기 때문에, 네트워크 문제로 환불 API 호출 자체가 실패하면 사용자는 실제로 사용하지 않은 크레딧을 잃을 수 있습니다. 이 위험을 완전히 없애지는 못했지만, 작업이 끝난 뒤에는 `fetchCredits()`로 백엔드 실데이터와 다시 동기화해 화면상의 오차를 제거하도록 했습니다. 즉 클릭 시점의 즉각적인 반응성은 낙관적 차감이 담당하고, 최종 정합성은 작업 종료 시점의 재동기화와 워커 트랜잭션의 멱등성 체크가 함께 담당하도록 역할을 나눴습니다.

## 결과 및 회고

사용자가 보유한 크레딧 범위 밖으로 요청이 새어나가는 초과 인출은 이 구조로 막혔고, 버튼 클릭과 동시에 잔여 크레딧이 바뀌는 즉각적인 반응성도 함께 얻었습니다.

1. **이번 문제는 이전에 내린 결정(워커 트랜잭션으로 차감 시점을 옮긴 것)이 만들어낸 부작용이었습니다.** 하나의 동시성 문제를 해결하면 그 해결책이 다른 층위에서 새로운 타이밍 공백을 만들 수 있다는 것을, 원자성 문제와 연타 문제를 순서대로 겪으며 확인했습니다.
2. **완벽한 동기화보다 "먼저 차감하고 실패하면 되돌린다"는 단순한 순서 하나가 타이밍 공백을 훨씬 저렴하게 막아줬습니다.** 서버와 매번 동기적으로 잔여량을 확정하는 예약 시스템은 이 문제의 크기에 비해 과도한 설계였습니다.
3. **즉각적인 반응성(낙관적 차감)과 최종 정합성(워커 트랜잭션 + 재동기화)을 하나의 메커니즘으로 합치려 하지 않고 역할을 나눈 것이 유효했습니다.** 클릭 순간의 UX와 데이터의 최종 정확성은 반드시 같은 시점에, 같은 메커니즘으로 보장될 필요가 없었습니다.
