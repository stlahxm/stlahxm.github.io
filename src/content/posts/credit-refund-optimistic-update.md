크레딧 로직은 이번이 처음 손대는 게 아니었습니다. 이 글은 두 번째 사건이 왜 첫 번째 해결책의 결과물이었는지를 시간 순서대로 정리한 기록입니다.

## 1차: 결과와 차감이 따로 놀던 문제 (이미 해결됨)

원래는 AI 분석 결과 저장과 크레딧 차감이 프론트엔드에서 각각 별도로 Firestore에 쓰는 구조였습니다. 네트워크가 불안정하거나 탭이 종료되면 결과만 저장되고 차감은 빠지거나, 반대로 차감만 되고 결과는 유실되는 정합성 문제가 있었습니다.

이건 이미 다른 작업에서 고쳐둔 부분이었습니다. AI 분석을 실제로 수행하는 주체(워커)가 결과 저장과 크레딧 차감까지 하나의 트랜잭션으로 함께 책임지도록 옮기고, 멱등성 체크(이미 `completed` 상태면 재처리하지 않음)를 더해 원자성 문제를 해결했습니다.

크레딧이 "분석 완료 후"에 차감되는 지금의 구조는 이 1차 개선의 결과물입니다. 후불제 자체는 버그가 아니라 의도된 설계였습니다.

## 2차: 그 해결책이 만든 새로운 지연 구간

크레딧 차감이 워커에서 비동기로 처리되는 이상, 요청이 접수된 시점과 실제로 차감이 반영되는 시점 사이에는 필연적으로 지연 구간이 생깁니다. 크레딧이 5개 남은 사용자가 이 지연 구간 안에서 6번 이상 연속으로 요청을 보내면, 앞선 요청들의 차감이 아직 반영되지 않았기 때문에 뒤따르는 요청들도 프론트엔드의 잔여 크레딧 체크를 전부 통과했습니다.

그 결과 DB 데이터가 마이너스로 내려가는 부정합과, 크레딧이 없는데도 AI 분석이 계속 실행되는 서버 자원 낭비(Overdraft)가 함께 발생했습니다.

이 문제는 악의적인 공격이 아니라 정상적인 UI 연타만으로도 재현됐습니다. 그리고 중요한 건, 이게 1차 개선이 잘못돼서 생긴 문제가 아니라는 점이었습니다.

"결과와 차감을 원자적으로 묶는다"는 결정은 정합성 문제를 정확히 해결했지만, 그 대가로 "차감 시점이 분석 완료 이후로 미뤄진다"는 새로운 성격의 공백을 만들었습니다. 첫 번째 문제를 제대로 풀었기 때문에 두 번째 문제가 생긴 셈이었습니다.

## 3차: 먼저 깎고, 실패하면 되돌리기

정확한 잔여량을 서버와 매 요청마다 동기적으로 확정하는 예약 시스템도 검토했지만, 구현 복잡도가 이 문제의 크기에 비해 컸습니다. 대신 다음 방식을 선택했습니다.

- **프론트엔드**: 버튼 클릭 즉시 UI 상의 크레딧을 먼저 차감(낙관적 차감)해, 다음 클릭이 곧바로 남은 크레딧 부족으로 막히도록 했습니다.
- **AI 백엔드**: 작업이 실패하면 그 시점에 환불 API를 호출해 차감분을 되돌립니다.

```java
// MemberRestController.java — 환불 API
@PostMapping("/usage/refund")
public ApiResponse<Void> refundUsageCount(@Valid @RequestBody RefundUsageRequest request) {
    memberCommandUseCase.refundUsageCount(request.getUid(), request.getTaskId());
    return ApiResponse.onSuccess(null);
}
```


```tsx
// page.tsx — 클릭 즉시 UI 반영
const generate = async () => {
```

성공 시에는 별도의 차감 API를 호출하지 않습니다. 프론트엔드가 클릭 시점에 이미 차감을 반영했기 때문입니다.

크레딧 차감과 결과 저장의 원자성을 지키는 역할은 여전히 1차 개선 때 만든 워커 트랜잭션이 담당하고, 낙관적 차감은 그 트랜잭션이 완료되기 전까지의 UI 반응성만 담당하도록 두 메커니즘의 책임을 나눴습니다.

## 지금 남은 리스크

낙관적 차감을 도입한 뒤에도 완전히 사라지지 않는 위험은 있습니다. 프론트엔드가 먼저 차감을 반영하고 서버 응답을 기다리는 구조이기 때문에, 네트워크 문제로 환불 API 호출 자체가 실패하면 사용자는 실제로 사용하지 않은 크레딧을 잃을 수 있습니다.

이 위험을 완전히 없애지는 못했지만, 작업이 끝난 뒤에는 `fetchCredits()`로 백엔드 실데이터와 다시 동기화해 화면상의 오차를 제거하도록 했습니다. 클릭 시점의 즉각적인 반응성은 낙관적 차감이, 최종 정합성은 작업 종료 시점의 재동기화와 워커 트랜잭션의 멱등성 체크가 나눠서 책임집니다.

## 회고

1. **이번 문제는 이전에 내린 결정이 만들어낸 부작용이었습니다.** 하나의 동시성 문제를 해결하면 그 해결책이 다른 층위에서 새로운 타이밍 공백을 만들 수 있다는 것을, 정합성 문제와 연타 문제를 순서대로 겪으며 확인했습니다.
2. **완벽한 동기화보다 "먼저 차감하고 실패하면 되돌린다"는 단순한 순서 하나가 타이밍 공백을 훨씬 저렴하게 막아줬습니다.** 서버와 매번 동기적으로 잔여량을 확정하는 예약 시스템은 이 문제의 크기에 비해 과도한 설계였습니다.
3. **즉각적인 반응성과 최종 정합성을 하나의 메커니즘으로 합치려 하지 않고 역할을 나눈 것이 유효했습니다.** 클릭 순간의 UX와 데이터의 최종 정확성은 반드시 같은 시점에, 같은 메커니즘으로 보장될 필요가 없었습니다.
