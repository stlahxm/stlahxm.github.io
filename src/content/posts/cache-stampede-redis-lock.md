캐싱 설계는 한 번에 완성되지 않았습니다. 이 글은 캐시 구조가 세 번 바뀌는 동안 각 버전이 왜 다음 버전으로 대체됐는지를 기록한 것입니다.

## v1: 최종 결과를 통째로 캐싱

가장 먼저 검토한 방식은 파일 해시 하나로 최종 분석 결과 자체를 캐싱하는 것이었습니다.

```
cache_key = sha256(file_bytes) + ":" + mode + ":" + lang + ":" + sha256(json_sorted(settings)) + ":" + MODEL_VERSION
```

동일한 강의 자료를 여러 학생이 각자 업로드하는 상황을 겨냥한 설계였지만, 실제로는 사용자별 설정(learner profile)이 최종 결과에 영향을 줬습니다. 요약 길이, 문제 개수, 문제 유형, 난이도 같은 옵션이 조금만 달라도 캐시 키가 완전히 갈렸고, 두 사용자가 정확히 같은 설정으로 요청하지 않는 한 캐시는 적중하지 않았습니다. 캐시는 만들었지만 거의 아무도 그 캐시를 다시 만나지 못하는 구조였습니다.

## v2: 사용자 설정과 무관한 부분만 캐싱

모릭은 하나의 문서로 요약, 퀴즈, 시험 정리 등 여러 기능을 제공하는데, 이 기능들은 공통적으로 문서 구조를 분석하는 단계(Phase 0·1)를 거칩니다. 이 단계는 사용자가 무엇을 요청하든 문서 내용만으로 결과가 동일합니다. 그래서 최종 결과가 아니라 이 Phase 0·1 결과만 캐싱하는 방향으로 재설계했습니다(`{file_hash}:{mode}:v1:ALL` 키). 이 결과를 저장하는 테이블(`analysis_cache`)을 추가하고 나니, 같은 문서를 요약 → 퀴즈 → 시험 정리 순서로 반복 요청할 때의 중복 연산은 확실히 해결됐습니다.

하지만 여기서 새로운 문제가 나타났습니다. 문서 하나를 분석하는 데는 평균 5분이 걸렸고, 같은 문서를 여러 사용자가 거의 동시에 업로드하면 첫 번째 워커가 분석을 마쳐 캐시를 저장하기 전까지는 모든 요청이 Cache Miss를 만났습니다. 결국 여러 워커가 같은 문서를 동시에 분석하면서 동일한 AI 호출이 반복 실행되고 있었습니다. 캐시 적중률을 높이는 것과 캐시가 채워지기 전의 빈 시간을 막는 것은 서로 다른 문제였습니다.

처음에는 PostgreSQL의 `UPSERT`(`ON CONFLICT DO UPDATE`)로 이 공백을 막을 수 있다고 생각했습니다. 하지만 `UPSERT`가 개입하는 시점은 AI 분석이 모두 끝난 뒤, DB에 저장하는 순간이었습니다.

```
요청 A → AI 분석 시작
요청 B → AI 분석 시작
요청 A → AI 분석 완료
요청 B → AI 분석 완료
        ↓
둘 다 DB 저장 시도 → UPSERT가 중복 저장 방지
```

DB 데이터는 정상적으로 유지되지만, 이미 두 번의 AI 호출 비용과 연산은 발생한 상태였습니다. 막아야 할 건 "데이터 중복 저장"이 아니라 "같은 작업의 중복 실행"이었고, 그 지점은 저장 단계가 아니라 분석이 시작되기 직전이었습니다.

## v3: 분석 시작 전에 락을 걸기 (현재 구조)

중복 AI 호출을 줄이기 위해 PostgreSQL Row-level Lock과 Redis 분산 락을 비교했습니다.

1. **PostgreSQL Row-level Lock(`FOR UPDATE`)**
   - 장점: 같은 문서에 대한 요청이 들어오면 하나만 처리하고 나머지는 DB Lock을 기다리게 할 수 있습니다.
   - 단점: AI 분석 시간이 수 분에 달하는 서비스에서는 이 대기 시간 동안 DB Connection을 계속 점유하게 됩니다. 중복 호출은 줄여도 DB Connection Pool이 부족해지는 다른 문제가 생겨 기각했습니다.
2. **Redis 분산 락 + ARQ 지연 재시도 (최종 채택)**
   - 장점: 락을 획득한 워커만 AI 분석을 진행하고, 나머지는 DB 커넥션이나 서버 워커를 계속 붙잡지 않은 채 대기 없이 큐로 돌아갑니다.
   - 단점: Redis 자체가 장애를 일으키면 락 획득 여부를 판단할 수 없다는 새로운 의존성이 생깁니다.

```python
lock_key = f"cache_lock:{cache_key}"
acquired = await redis.set(lock_key, "1", nx=True, ex=900)  # TTL 900초
```

락을 획득하지 못한 워커는 `raise Retry(defer=30)`으로 30초 뒤 재시도하도록 큐에 다시 넣었고, 그사이 락을 획득한 워커가 분석을 마쳐 캐시를 저장하면 재시도 시점에 Cache Hit으로 전환됩니다. 락의 TTL은 캐시 공백 구간(약 5분)보다 넉넉한 15분으로 설정해, 분석이 예상보다 길어져도 락이 먼저 풀려 다른 워커가 같은 문서를 중복으로 다시 시작하는 상황을 방어했습니다. Redis 장애 시에는 락 획득 함수 자체가 예외를 삼키고 `True`(락 획득 성공)를 반환하도록 Fail-safe로 설계했습니다. 락 없이 진행되면 중복 연산 비용은 감수하더라도, Redis 장애가 전체 분석 파이프라인을 막는 상황만큼은 피하기 위한 선택이었습니다.

## 캐시를 위해 프롬프트까지 손봐야 했다

v2에서 v3로 넘어오면서 하나 더 손봐야 했던 부분이 있었습니다. Phase 0·1 결과를 여러 사용자가 공유하려면, 그 단계의 프롬프트 자체가 사용자별 설정에 의존하지 않아야 했습니다. `settings={"_neutral": True}`를 전달하면 사용자별 학습 프로필 지시문을 빈 문자열로 반환하도록 중립화 로직을 추가해, Phase 0·1 결과가 특정 사용자의 설정에 묶이지 않고 모든 사용자가 재사용할 수 있게 만들었습니다. Phase 2(최종 합성)는 이 중립화를 적용하지 않고 항상 사용자 설정을 반영해 실행합니다.

같은 김에 모델도 나눴습니다. 반복 호출 가능성이 높고 결과 형태가 비교적 단순한 Phase 0·1은 `Gemini 2.5 Flash-Lite`로 낮췄고, 사용자가 직접 확인하는 최종 결과 생성 Phase 2는 품질을 위해 `Gemini 2.5 Flash`를 유지했습니다.

## 결과 및 회고

| 지표 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 중복 문서 캐시 적중률 | 0% | 21.6% |
| 월간 절감 AI 호출 비용 | — | 100만 토큰 이상 |
| 캐시 조회 속도 | DB 조회 방식 | 0.07ms 수준 |

1. **v1이 실패한 이유를 정확히 짚어야 v2가 가능했습니다.** 캐시 키에 설정 해시까지 포함시키면 정합성은 완벽하지만, 그만큼 캐시가 적중할 조건도 좁아집니다. "무엇이 재사용 가능한 단위인가"를 사용자 설정과 무관한 Phase까지 거슬러 올라가서 다시 정의한 뒤에야 캐싱이 실제로 효과를 냈습니다.
2. **UPSERT는 데이터 정합성을 지켜주지만, 이미 발생한 연산 비용까지 되돌려주지는 못했습니다.** 캐시가 채워지기 전의 공백 구간을 막으려면, 중복을 차단하는 지점을 저장 시점이 아니라 연산이 시작되기 직전으로 옮겨야 했습니다.
3. **캐시를 공유 가능하게 만드는 작업은 저장 로직뿐 아니라 프롬프트 설계까지 함께 손봐야 하는 일이었습니다.** 프롬프트 중립화 없이는 같은 문서라도 사용자마다 결과가 미묘하게 달라 캐시가 무의미했을 것입니다.
